# A01 — otlp-grpc-traces-accepted

## Surface

Aperture (OTLP ingest gateway). Operator/integrator-facing.

## Behaviour

Given aperture is running with both listeners bound (gRPC `:4317`, HTTP
`:4318`)
And a sink is configured (any of `stub` or `forwarding`; A01 is
agnostic to the choice — round-trip-to-downstream is E01's job)
When an OTLP/gRPC client sends an `ExportTraceServiceRequest`
containing N spans to `:4317`
Then aperture acks the request (gRPC OK)
And aperture's stderr emits one
`event=sink_accepted signal=traces span_count=N` line
naming the resource's `service.name`.

## Issues

- [`issues/001-aperture-binary-ignores-config-flag.md`](../../issues/001-aperture-binary-ignores-config-flag.md) —
  related, not blocking. Aperture at this SHA does not parse the
  `--config` file; the binary's `main()` runs with hardcoded
  defaults, so the harness's `kind = "forwarding"` is silently
  ignored and the StubSink is what actually accepts. A01 is
  satisfied because the contract is sink-agnostic, but the issue
  blocks E01-E06 (round-trip) and several other expectations.

## Notes

The `sink="stub"` field in the matched stderr line is a present-tense
observation, not a contract violation. A01 says "the configured sink
receives"; with the binary running on defaults, the configured sink is
StubSink. Once slice-07 lands the `--config` loader, the harness will
re-verify A01 with `kind = "forwarding"` and expect `sink="forwarding"`
in the stderr line. The contract on `signal`, `span_count` and
`resource.service.name` is unchanged.
