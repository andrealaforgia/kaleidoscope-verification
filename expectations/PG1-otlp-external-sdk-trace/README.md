# PG1 — otlp-external-sdk-trace (OTLP compatibility proven by a real external app)

## Surface

Product goal PG-1 (agreed PO↔Customer): Kaleidoscope is OTLP-compatible with a
STANDARD external OpenTelemetry SDK, not only self-compatible. This is the
repeatable, committed black-box regression net that cements the Customer's
ad-hoc proof.

## Behaviour

A readable external demo app (`pg1_app.py`) using the official OpenTelemetry
Python SDK ONLY (`opentelemetry-sdk` + `opentelemetry-exporter-otlp-proto-http`,
zero Kaleidoscope code) exports a parent+child trace over the real OTLP/HTTP
wire to the consolidated runtime's ingest (:4318). The trace is then retrieved
by trace-id from the trace query API (:9092) and checked against exactly what
the app sent:

1. external official SDK, no Kaleidoscope code, real OTLP wire.
2. parent+child tree survives end-to-end: the retrieved trace has exactly one
   root (no `parent_span_id`) and a child whose `parent_span_id` == the root's
   `span_id`, and both match the app's own span ids.
3. `customer.id="bea-test"` is present in the retrieved child span's attributes
   (span-level, PO-confirmed).
4. retrieved `start/end_time_unix_nano` EXACTLY round-trip the app-sent values,
   and the parent window encloses the child
   (`parent.start ≤ child.start ≤ child.end ≤ parent.end`).

Bonus (non-blocking, PG-2 seed): a log emitted INSIDE the active span is
retrievable on :9091 carrying the same `trace_id` — so log↔trace correlation
already works from an external SDK. It also surfaces the PG-2 criterion-5
inconsistency black-box: the logs API serialises `trace_id` as a byte-integer
array while the traces API renders it as a lowercase-hex string.

## How to run

```
cd ~/dev/kaleidoscope-expectations
KALEIDOSCOPE_REPO=~/dev/kaleidoscope bash harness/run-expectation.sh PG1
```

It builds the consolidated runtime from the committed HEAD snapshot, boots it
(`KALEIDOSCOPE_TENANT=acme`) on a private docker network, runs the external
Python OTel app in a `python:3-slim` container (`pip install opentelemetry-sdk
opentelemetry-exporter-otlp-proto-http`) exporting to the runtime over OTLP/HTTP,
then queries :9092 `/api/v1/traces/by_id` and checks the four criteria
(`pg1_assert.py`).
